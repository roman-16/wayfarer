# Playtest

`just test` proves the pack boots, no hall grows on its own and the stronghold ring sits at its radius. It cannot judge how anything looks, sounds or feels. That is the user's, in game.

## Hand the user a checklist

The `finish` skill comes first: its walkthrough finds and fixes what would leave a player stuck, confused or crashed, so this checklist keeps only what play alone shows, the shader, the far view, sound, motion and feel. Pick the items the change touched, and give each as one line: where to go, what to do, what should happen. `just showroom` opens the showroom, where every hall stands in a row and the compass points at a waymark 750 blocks west of the camp; `/locate structure wayfarer:hall/<eye>` and `/tp` find the halls in the natural world next to it. `just play` opens a fresh world in survival, for everything that has to be met the way a player meets it. `python3 scripts/client.py start --state <quest/step> --visible` opens the world at any step of the story, such as `ash/the_door`, with every step before it played. All of them run without shaders, without Distant Horizons (unless started with `far`, which keeps a far view of 1,024 blocks) and at 8 chunks, so shaders, the far view and anything judged by its look in the world are checked in the published pack, which a Prism instance imported once from `https://roman-16.github.io/wayfarer/Wayfarer.zip` fetches before every launch.

## A blind play

At the bar and at the end of each act, friends who never read `design/` play on the exaroton server with only what the screen shows (`design/production.md`, R3). The agent's `playthrough` plays the same stretch first, so the friends' evening goes to how it feels, not to bugs. Nobody who knows the design helps or explains during the play; the designer watches and notes where they hesitate. The server is recorded while they play (Record a play), and the session record shows where the team stalled and how long each step took. Every stall the screen did not explain is a finding for the `playthrough` skill's questions; every "this was boring" goes back to the quest's design. The voice joins the plays as its lines are recorded (`design/narration.md`).

## Record a play

`just exaroton` records the account's server into `exaroton/<YYYY-MM-DD_HH-MM>/`, in the repository root and ignored by git. It needs `EXAROTON_API_TOKEN`, which devbox loads from `.env`; never print the token or write it anywhere else. With more than one server on the account, name it: `just exaroton roman168`.

Run it in the foreground with no timeout: it records until the user presses Escape, which kills it and ends the turn; never start it in the background. Its first line names the world exaroton opens and warns when the road was last carried to another one; then it prints one line per status change, stream start and reconnect, and one when region files vanish or shrink between two polls, and waits through an offline server until it boots.

The recorder only reads. Never send console commands, and never call `start`, `stop`, `restart`, `command`, `extend-time`, `logs/share` or any `POST`, `PUT` or `DELETE` endpoint, nor any websocket message but a stream `start`; exaroton makes `start`, `stop` and `restart` plain `GET`s, so reading is not safe by method alone. Two things write to the server: `just carry <server> pack`, which puts the server pack `just pack` built on it, and `just carry <server> upload` (Carry the road to a new world).

| File | Holds |
|---|---|
| `session.json` | At the start: the server object, its RAM, every `server.properties` value and the mods folder with sizes |
| `console.log` | Every console line as it arrives, without ANSI codes; lines carry only `[HH:MM:SS]` |
| `streams.jsonl` | One timestamped JSON line per websocket message: `status` (with players), `heap` (`usage` in bytes), `stats` (`memory.usage`, `memory.percent`), `tick` (`averageTickTime` in ms), `connected`, `disconnected` |
| `polls.jsonl` | Every minute: status, players, region file count, empty region files, region bytes, the region files gone or smaller since the poll before with their sizes, and the Distant Horizons database size, or the error that stopped the poll |
| `latest.log` | The full server log with millisecond timestamps, refreshed every five minutes while the server runs and once when it stops or crashes; while it runs it lags about ten minutes behind |

Every line is written as it arrives, so a session is complete up to the moment it stopped. The tick stream has stayed silent on this server and exaroton reports no CPU usage; "Can't keep up!" lines in `console.log` and `latest.log` measure the server's lag.

## Bring the results back

Start with the play record: `just play-report exaroton/<session>` prints each step's time, every stall with what each player did, said and looked at, the choices, deaths, the rain, screens and frames, and draws everyone's paths into `report/paths.png` in the session's folder; its stalls go first among the findings, beside the user's notes.

Then read what the user's own game wrote while they played: the Prism Launcher instance at `~/.local/share/PrismLauncher/instances/Wayfarer-<version>/minecraft/` keeps `crash-reports/`, `logs/latest.log` and the gzipped logs before it. Every crash there is a finding of its own, fixed at its cause before the user's notes; the log's story lines (`story music`, `sound`, `Tollbridge stands`, deaths, `[CHAT]`) time what the notes describe, so a "too fast" or "came too early" gets its seconds from the log, not a guess.

Every number the user wants changed goes to `balance.toml`, or to the mod's config in `pack/config` when it is another mod's number. Worldgen numbers (the world's shape, the ring's radius, structure spread) only change new chunks: test them in a fresh world. A place's distance ahead (`ahead_blocks`) holds for every place not yet put down.

Every play on the server ends with its road carried to a new world, so the next one meets what changed: once its findings are fixed, put the new server pack on the server and carry it as below, unasked.

## Carry the road to a new world

After every play, once its findings are fixed, run `just pack` and `just carry <server> pack`, which puts the new server pack on the server while it is offline (the mods, configs and JourneyMap settings of `build/server`, only what changed, and what the pack dropped removed; it refuses when the server runs another NeoForge than the pack), then run `just carry <server>` in the foreground with a generous timeout while the server is offline. When the play stopped at a step that broke, `just carry <server> <quest/step>` carries the road back to an earlier step of the main quest under way instead, such as `the_keepers_apprentice/the_smoke`, so the team plays that step again from its start, everything they learned after it still in their journal; a step of another quest or one ahead of the road is refused. The carry changes nothing on exaroton:

1. It downloads what the carry uses of the server's world into `exaroton/<YYYY-MM-DD_HH-MM>-carry/old/`: the players, the world's data without Lootr's, the tents' insides, the land and the rivers' data. exaroton hands out one file a request and slows a fast caller down, so this takes most of the carry's 15 minutes or so.
2. It opens that world on the dev server with every player brought in by their id, and packs what stands in the world into its owner, as the player's own actions would: every pitched tent into the inventory with everything in it, every grave taken back, their own stone taken up, and the caravan's horse into the caravan. The player's last fire, respawn point, stillness and touched waystones are forgotten.
3. It grows a new world from a random seed (another one, up to four, when the land cannot hold the story) and plays it to the step the main story stands at, with the team's own answers and the stranger's stone as they wrote it, then lays in what the team knows (choices, talks, the journal, rewards and who took them, gifts, trust, the halls taken, deeds, the captains' pages handed out, the dice and the smith's work) and every player's things (player data, backpacks, tents' insides, horses bound to a horn) into `exaroton/<...>-carry/new/`.

Then run `just carry <server> upload` and show the user both summaries. It refuses unless the server is offline, its world unchanged since the download and its mods those of `build/server`, the server pack `just pack` builds and `just carry <server> pack` puts on the server; it uploads the world as `world_<YYYY_MM_DD_HH_MM>` (exaroton turns every other character of a World name, such as `-`, into `_`), sets it as the World name in the server's options (exaroton writes `server.properties` from them at every start, so a change to the file alone is lost) and fails when exaroton does not keep it, keeps the world before on the server as the way back, and removes every other world a carry put there.

What the team meets on joining: everyone stands where the step begins, at its hour, and every step under way, main or side, begins again; a grave's things that found no room stay behind, named in the summary, and so do boats, ships, pets and horses not bound to a horn that stood in the world; the new world starts its own play record; Distant Horizons and JourneyMap start fresh on every machine by themselves, since the seed and the world's id are new.
